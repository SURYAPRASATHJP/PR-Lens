**The query variant decides more than the model does.** Hunk as reviewed beats
the before-state by 2.3x at @10 on the same pairs and the same index. The
before-state rule came from the Phase 2 spec and was wrong: `diff_hunk` is frozen
at the commit the comment was made on, so it cannot contain the fix, and
stripping the + lines removes the code under review rather than the answer.

**Fusion does not earn its place.** RRF against the better of its two inputs at
@10: +0.000, +0.005, +0.002, -0.005. Every one inside its own interval. Four
comparisons, no gain. Drop RRF and keep the simpler stack.

## 2. Leakage, measured

A review comment unit carries the `diff_hunk` it was left on, so querying with
that hunk finds the gold by string match. The eval index re-serialises comments
body only. The gap is what that rule is worth.

    query              retriever            with hunk @10   body only @10   gap
    hunk as reviewed   BM25                 0.998           0.185           +0.814
    hunk as reviewed   dense gte            0.977           0.222           +0.754
    hunk as reviewed   RRF gte + BM25       0.995           0.217           +0.778
    before-state       BM25                 0.930           0.087           +0.842

Without the body-only rule this table would have reported 0.98 and meant nothing.

## 4. The reranker plateau, which turned out to be a decline

Cross-encoder over the first N of the RRF list, body-only, fixed 300-pair sample.
First stage @n is the ceiling: reranking reorders candidates, it cannot add one.

    query: hunk as reviewed
    N     first stage @n   reranked @1   reranked @5   reranked @10
    5     0.160            0.027         0.160
    10    0.213            0.027         0.187        0.213
    15    0.240            0.017         0.173        0.230
    20    0.277            0.020         0.173        0.257
    30    0.300            0.020         0.167        0.253

**The reranker makes retrieval worse.** At N=30 it turns a ceiling of 0.300 into
0.253. Its @1 of 0.020 is below the first stage's own @1 of 0.045. Giving it more
candidates makes it worse, not better, which is the signature of a scorer that is
not measuring the right thing.

It is not a broken model. It is the wrong relation. A cross-encoder is trained on
"does this document answer this query". Here the relation is "would a reviewer
say this about this code", and nothing in its training makes those the same
question. Section 6 adds the second reason: 25 seconds per query.

## 5. Filtering: pre-filter, never post-filter

Dense gte, body-only. Post-filter fetches C candidates from the whole index and
drops what the filter rejects, which is what pgvector's HNSW does with a WHERE
clause. C = 40 is its default `hnsw.ef_search`. The gold always passes the
filter, so every loss is the candidate budget running out.

    repo AND kind=review_comment, 0.81% of the index. Query: hunk as reviewed
    search                  recall@10   mean results   queries short of 10
    pre-filter, exact       0.475       10.0           0.0%
    post-filter, C = 10     0.222       1.0            100.0%
    post-filter, C = 40     0.316       2.6            95.7%
    post-filter, C = 100    0.377       4.3            82.5%
    post-filter, C = 400    0.443       7.3            48.1%

At pgvector's default, a filtered search returns 2.6 results when it was asked
for 10, and 95.7% of queries come back short. The collapse is not subtle and it
is not a tuning problem: C = 400 is ten times the default and still loses 0.03.

Note what else this row says. Pre-filtered within a repo, recall@10 is 0.475
against 0.222 unfiltered. Restricting to the repo under review, which serving
does anyway, roughly doubles recall.

## Known limitations of v1

1. **All-addition hunks are excluded.** 1002 comments were dropped for having no
   before-state, so new files and pure additions are absent. They were dropped so
   both query variants could be scored on identical pairs. Now that hunk as
   reviewed is the headline, the constraint has outlived its reason, and those are
   exactly the hunks where the system has least context. Fix in v2.
2. **623 of 1853 pairs carry a suggestion block**, whose code overlaps the hunk
   lexically. That is residual leakage inside the body-only index, affecting a
   third of the set. Measure it as its own row in v2 rather than assuming it small.
3. **The acknowledgement filter is dead weight.** It caught 8 comments. `short`
   reaches them first, because "LGTM" is four characters.
4. One gold document per query understates practical utility: a different comment
   making the same point is useful to a drafting step and scores zero here.
